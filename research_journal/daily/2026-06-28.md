## Symptom-driven retrieval implemented (the approved redesign)

**Why.** Our expert Dr. Sunita T. Pandey said the classical texts are **general and symptom-based, not crop-specific** — a remedy given for a symptom applies across plants showing it (her kunapajala work was validated on potato among many crops). Deep web research confirmed it (24/25 claims verified, 3-vote adversarial): Vrikshayurveda classifies affliction by symptom + dosha, not by crop, and a peer-reviewed Vrikshayurveda expert system diagnoses purely from symptom questions and never asks the crop. Dr. Akshay Pandey approved the change.

**The flaw this fixes.** Our pipeline was effectively treating the corpus as a *crop-indexed database*: the query led with the plant name, and when that name wasn't in the texts the generator refused ("not enough information"). That is unfaithful to how these texts actually work, and it was *under-reporting* real coverage (e.g. corn/potato refusals that shouldn't have been refusals).

**Two changes, both faithful to the sources:**
1. `src/integration/strategy_llm_mediated.py` — Strategy B now states up front that the treatises are general/symptom-based, adds a **"LEAD WITH THE SYMPTOM"** rule (crop may appear once, late; never as the subject; the crop-led anti-patterns "what does <crop> disease look like" / "remedies for <crop>" are explicitly banned as poor-retrieval), and the structured context demotes the crop to *"background context only — the texts are not crop-specific"*. The detected disease label is still carried and translated into its symptom family (the earlier parroting fix stands).
2. `src/rag/generator.py` — added **rule 1a** to the §17 grounded-advisor prompt. The faithfulness guardrail is untouched; what changed is its *scope*: a passage addressing the observed condition now counts as sufficient evidence **even if it never names the crop**, so the model must not refuse merely because the crop is absent. It refuses only when no passage addresses the condition at all, and must state plainly when leaning on a general passage.

**Nuance kept honest.** Surapala does contain a minority of crop-named recipes (mango, pomegranate, coconut), so the framing is "predominantly symptom-general", never an absolute claim.

**Validated.** New `tests/integration/test_symptom_driven.py` (7 tests) locks in: symptom-led framing, the lead-with-symptom rule, crop demotion, disease label retained, the refusal guardrail still present, refusal correctly scoped, and honest flagging of general passages. **Full suite: 314 passed.**

## Scope gate — the farmer declares the plant (Ankit's design, and it's the better one)

**The flaw in what we had.** The crop was auto-derived from the disease label. But the classifier has a **fixed 27-class head and cannot say "I don't know"** — given an untrained plant (brinjal, rice…) it still returns its closest class and shows it *confidently*. So using the model to decide "is this plant supported?" asks it a question it structurally cannot answer.

**Ankit's proposal, adopted:** let the **farmer select the plant** from a dropdown of the trained plants (+ "Other" → type the name). Clean division of labour — **the farmer knows the plant, the model knows the disease.** Scope is then settled with certainty *before any model runs*.

**Implemented:**
- `app_config.supported_crops()` derives the plant list from the model's **own `class_names`** (13 crops from the 27 classes), so the UI's honest-scope list can never drift from the checkpoint.
- Plant selector moved beside the uploads as a required step; "Other" requires typing the name.
- **Out-of-scope short-circuits before inference** with an honest *"…it will not guess"* message + the supported list.
- The disease label's implied crop is now a **cross-check only**: on disagreement we warn (*"you selected tomato but this looks like potato"*) **without blocking** — the farmer stays the authority on their own crop.

## Adaptive learning — feedback collection (human-in-the-loop)

Dr. Pandey asked whether the system can learn from new inputs. Agreed form: **not** live self-learning (unverified labels would poison the model; naive retraining also risks catastrophic forgetting). Instead: **collect → expert validates → offline retrain**.

**Storage decision.** Ankit correctly flagged that a SQLite file on Colab is wiped when the session ends — samples would silently vanish. Also, the end goal is a farmer-facing app, not Colab. Chose the **private HF dataset** (`iks-feedback-samples`): persists, already authenticated in our notebooks, shareable with the agronomy expert. Deliberately did *not* build a multi-backend abstraction — unnecessary now; a real DB can be swapped in when the app is built.

**Design detail that matters:** one **self-contained record per sample** (`images/<id>.jpg` + `records/<id>.json`) rather than appending to a shared index file — so concurrent submissions can never clash or overwrite each other. Every sample arrives `status="pending_expert_review"` with `expert_label=None`; **nothing is training truth until an expert says so.**

**Collected cases:** out-of-scope plants (the farmer's typed name is the only label we have — and it's what makes the sample useful), plus low-confidence predictions and crop mismatches. Upload is **best-effort and never fatal** — no token/network must not break a farmer's advisory.

**Validated:** `tests/test_scope_gate.py` (5) + `tests/test_feedback.py` (6), including that a broken Hub returns `None` instead of raising.
